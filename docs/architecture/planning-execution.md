# 계획·실행 상태와 제출 보호

기존 작업 분류(recipe)와 별개로 `unknown / planning / ready / executing / review` 단계를 둔다. 모델·추론·Plan 모드도 서로 다른 관측값이다. 상태 저장, 지침 출력, 실제 서비스 적용은 같은 사건이 아니다.

## 책임과 데이터

| 위치 | 책임 |
| --- | --- |
| packages/contracts | 프리셋·단계·관측·보호 상태의 공통 형식 |
| packages/guidance | 로컬 요청 분류, 단계별 짧은 지침, 평가 |
| integrations/codex | 실제 훅 입력을 제한된 관측과 요청 해시로 변환 |
| apps/desktop/src/features/workflow | 카드·계획 확인·수동 안내·설정 상태 |
| apps/desktop/src-tauri | 인증·채팅 바인딩·개정 검사·일회성 예외·저장 |

`workflow_preferences_v1`과 `workflow_tasks_v1`은 기존 DB에 별도로 추가한다. 기존 strict assistance 선호 JSON, 앱 식별자, 데이터 디렉터리, 펫 위치는 유지한다. 최초 기본값은 balanced·planFirst이며 enabled는 false다. 기존 작업에는 저장 당시의 설정을 보존하고 기본값 변경을 일괄 적용하지 않는다.

계획 확인은 채팅·계획 개정·설정 개정에 묶인다. 계획을 관측하지 못했으면 요약은 빈 상태로 유지하고 사용자의 명시적 확인만 기록한다. 기록 변경과 설정 변경은 확인을 무효화한다. 한 번 예외는 요청 해시와 개정에 묶고 새 제출에서만 소비한다. 전체 요청 원문·첨부·대화 로그는 저장하지 않는다.

## 처리 순서

1. 입력의 세션·cwd·제출 ID를 검증하고 인증된 로컬 API로 요청한다.
2. 단계와 설정 개정, 해당 제출의 관측값을 바탕으로 preflight를 수행한다.
3. 검증된 보류 판정이면 준비 훅은 `decision:block`만 반환한다. 실행 시작 이벤트·지침 전달 receipt·자동 펫 배정을 만들지 않는다.
4. 관측 훅도 같은 제출의 판정을 확인한다. 비동기 관측 훅을 동기 보호 훅의 대체품으로 취급하지 않는다.
5. 진행 가능한 요청에만 기존 실행 이벤트와 필요한 단계 지침을 전달한다. 추가 지침과 helper를 합쳐 UTF-8 3KB 이하이고, 변경 없는 지침은 반복 전달하지 않는다.

재시작하면 관측값과 일회성 예외를 다시 확인한다. 중복 제출 ID는 예외를 추가 소비하거나 새 실행으로 기록하지 않는다. 연결 오류·시간 초과·오래된 정보는 의도한 정책 보류와 구분하고 원래 요청을 통과시킨다.

## 검증 경계

- 일반 호출자가 capability를 true로 올릴 수 없다. 현재 production의 실제 관측·보류·자동 변경은 미검증이다.
- 모델 일치만으로 추론이나 Plan 모드 일치라고 표시하지 않는다. 훅의 permission_mode를 실제 Plan 협업 모드와 동일시하지 않는다.
- 입력 보존·첨부 보존·단일 제출·동기 준비 훅 동작이 확인돼야 보류를 지원한다고 표시한다.
- 일회성 예외에는 첨부까지 포함한 요청 식별 검증이 추가로 필요하다. 공식 Codex 훅의 prompt 해시만으로는 같은 문구의 첨부 변경을 구분할 수 없으므로, 현재 훅이 이를 지원한다고 표시하지 않는다.
- 자동 변경은 사용자 지정 범위와 실제 계정의 사용 가능한 조합 안에서만 가능하다. 현재 자동 변경 어댑터가 없으므로 수동 안내를 제공한다.
- 기존 요청의 명시적 선택과 모델 고정이 프리셋보다 우선한다. 인용문·업무 자료에 등장한 모델 이름만으로 선택을 바꾸지 않는다.
- 원래 사용 권한·도구 승인·실행 중인 응답은 변경하지 않는다. 기존 `/v1/assistance`의 현재 턴 바인딩과 인증은 그대로 유지한다.
