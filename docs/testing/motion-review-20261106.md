## 실행

```powershell
node scripts/motion-review.mjs --label 기준
node scripts/motion-review.mjs --label 개선 --scale 1.5 --only S3,S5,S6
node scripts/motion-review.mjs --compare work/motion-review/<기준> work/motion-review/<개선>
```

- 자체 Vite 서버를 **1437** 포트(strictPort)에 띄운다. 개발 서버 1420을 쓰거나 종료하지 않는다. `--origin http://127.0.0.1:<포트>`로 이미 띄운 검수 서버를 지정할 수도 있다.
- 시나리오마다 새 헤드리스 Chromium 컨텍스트를 만든다. 검수 서버 외 요청은 모두 막는다. 클립보드는 꺼져 있고, 사용자 Chrome·설치 앱·DB·실제 채팅·네이티브 입력은 쓰지 않는다. 제품 AI 호출은 0회다.
- 결과는 `work/motion-review/<시각>-<이름>/`에 남고 덮어쓰지 않는다. 영상은 저장소에 넣지 않는다.
- `--strict`는 기대 동작이 하나라도 안 맞으면 실패로 끝난다. 기본값은 기록만 한다. 현재 기준은 아래 미충족 항목이 있어 strict 모드에서는 실패한다.

## 관찰

1. **자세가 툭툭 바뀐다.** 클립 안의 프레임은 `steps(1, end)`로 교체되고, 겹침 페이드는 클립을 바꿀 때만 쓰인다. 겹침 없는 교체가 대기 중 초당 약 1회, 탭·접근 직후 초당 약 3.3–3.8회다. 두 실행의 차이는 7% 안이다.
2. **받기 시작에 한 프레임 튐.** S6에서 `receive`가 시작될 때 스프라이트가 한 프레임에 12px(펫 높이의 9.3%) 이동한다. [`CompanionPet`](../../apps/desktop/src/features/pets/CompanionPet.tsx)의 받기 동작이 `translateX(-12px)`에서 시작하기 때문이다.
3. **펫 몸통으로는 옮길 수 없다.** 이동은 ⠿ 손잡이만 지원한다(S4 0px, S4H 285px).
4. **살짝 끌었다 놓으면 카드가 열린다.** S5에서 펫 위에서 눌러 40px 끌었다가 제자리에서 놓으면 클릭으로 처리된다. 배율 1과 1.5에서 모두 재현했다. 탭과 드래그를 구분하지 않는다.
5. **유지되는 계약.** 완료 반응 1회와 같은 완료 재수신 무시, 작업 중 접근이 작업 자세를 덮지 않음, 숨김·동작 줄이기 시 실행 중 애니메이션 0, 3마리 상태 분리, 작업·연결 명령 0건이 기준에서 지켜진다.
6. **가장 긴 프레임은 실행마다 크게 흔들린다(17–150ms).** 헤드리스 렌더러의 잡음이라 한 번의 실행으로 판정할 수 없다. 판정은 반복 실행의 분포로 하고, 임계값은 개선 전후를 같은 조건으로 여러 번 측정한 뒤 정한다. p95와 자세 지표는 안정적이었다.

렌더러 CPU는 0.05–0.15 CPU초/초였다. 헤드리스 전체 페이지 기준이며 설치 앱의 CPU·메모리가 아니다.

## 한계와 다음 행동

- 브라우저 무대의 창 이동·크기 변경은 흉내다. 투명창 클릭 영역, 실제 창 이동, Windows 배율, 다중 모니터는 별도 Windows 시험 세션에서 확인한다. 브라우저 통과를 네이티브 통과로 쓰지 않는다.
- Playwright 영상은 탐색 색인이 없어 비교 화면의 중간 탐색이 안 될 수 있다. **함께 재생**은 처음부터 재생한다. 각 영상에는 1–2초의 로딩 구간이 앞에 있다.
- 다음 개선(연속 모션, 탭/드래그 구분)은 같은 시나리오를 기준 커밋과 개선 브랜치에서 각각 실행한 뒤 `--compare`로 판단한다. 목표 조건은 다음과 같다.
  - S4·S5의 기대 동작 충족
  - S6의 한 프레임 튐 제거
  - 겹침 없는 자세 교체 감소
  - 위 5번 계약 유지
- 무대는 `startDragging` 중 `tauri://move` 위치를 펫 창에 전달한다. 개선판이 창 이동 속도로 흔들림을 만들면 이 경로로 검사할 수 있다. 실제 Windows에서 이동 이벤트가 연속으로 오는지는 아직 확인하지 않았다.
