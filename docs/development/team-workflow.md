# 세 사람과 각자의 AI가 함께 만드는 AutoPets

**한 작업 · 사람 담당자 한 명 · 브랜치 하나 · PR 하나.** 변경 이유와 결과는 사람이 한눈에 보고, 다음 AI는 이전 대화를 몰라도 이어갈 수 있게 남긴다.

바로 찾기: [작업 시작](#매번-작업을-시작하거나-이어갈-때) · [코드와 설명 규칙](#제작-컨벤션) · [PR 작성](#pr-설명-작성하기) · [큰 변경 논의](#큰-변경은-먼저-회의)

## 함께 지킬 제품 방향

AutoPets는 **좋은 스킬과 작업 설정을 쉽게 쓰고, 하던 일을 펫과 이어가는 서비스**다. 첫 대상은 Windows Codex를 이미 사용하지만 스킬·프롬프트·모델 설정에는 익숙하지 않은 사람이다. 마케팅·운영 담당자는 우선 타겟 가설이며 확정된 수요로 취급하지 않는다. 행사·캠페인 페이지는 대표 과제이며 제품 전체를 웹페이지 제작 도구로 제한하지 않는다.

기본 흐름은 **Codex에서 펫 호출 → 앱·오버레이 → 펫 선택·현재 채팅에 적용 → 같은 채팅에서 요청 → 진행 확인 → 결과·하던 작업 복귀**다. 할 일은 Codex에서 입력하고, 앱은 선택·설정·상태·재사용에 집중한다. 정상 연결 뒤 수동 복붙이나 화면 자동 조작을 요구하지 않는 경로를 우선한다.

- 설명보다 펫·결과·다음 행동을 먼저 보여준다. 화이트·뉴트럴 화면과 기존 입체 강아지를 유지한다.
- 처음 성공하는 편의, 정확한 작업 재개, 같은 설정 재사용을 우선한다. 새 펫·서비스·꾸미기 확대는 별도 결정이다.
- 개선 순서는 **작업을 막는 문제 → 잘못된 상태 → 불필요한 조작 → 시각적 완성도**다. 사용자 변화 하나를 작업 단위로 잡고 관련 없는 기능 확장을 섞지 않는다.
- 현재 방식은 **펫 하위 작업의 모델·강도 라우팅과 계획 프롬프트**다. 자동 훅·부모 모델 변경·실제 Plan 강제를 약속하지 않는다.
- 대상 ID·폴더·개정 확인, 데이터 보존, 채팅 격리, 중복 실행 방지는 시각 개선보다 우선한다. 보안·신뢰 승인을 우회하지 않는다.

## 처음 합류할 때

[승완·서연·도엽의 브랜치와 별도 작업 폴더 준비](three-person-start.md)를 참고한다. 개인 시작 브랜치와 실제 Issue별 작업 브랜치를 구분한다.

1. **자기 작업 공간 준비:** 저장소를 각자 별도 폴더에 받는다. 새 작업과 작업 재개 모두 아래의 최신 코드 확인 절차부터 진행한다. 자기 변경을 보존하고 다른 사람의 작업 폴더는 그대로 둔다.
2. **방향과 담당 확인:** 이 안내의 목적·현황·아래 우선순위를 읽고, 담당 Issue에 범위와 완료 기준을 적는다. 열린 PR과 다른 사람의 최신 변경을 확인하고, 관련 PR이 아직 병합 전이면 내 작업과의 관계와 진행 순서를 적는다.
3. **개발 화면 실행:** [README](../../README.md)의 접힌 **개발·검사** 안내에 따라 잠긴 의존성을 설치한다. 화면만 볼 때는 `pnpm dev`, 요소에 의견을 남길 때는 `pnpm dev:feedback`을 쓴다. 실제 설치 앱의 연결 성공과 브라우저 미리보기를 구분한다.
4. **새 작업으로 수정:** 최신 `origin/main`에서 Issue 번호를 넣은 `task/<번호>-<이름>` 브랜치를 만든다. PR에는 사용 흐름과 전후 비교, 확인 결과, 이어서 할 일을 적고 변경에 필요한 검사만 수행한다.

### 매번 작업을 시작하거나 이어갈 때

최신 코드를 받아 두고 작업해야 이미 고친 부분을 다시 만들거나 다른 사람의 변경을 놓치는 일을 줄일 수 있다. `main`은 함께 쓰는 기준 브랜치(작업의 갈래)이고, `origin/main`은 내 PC가 마지막으로 받아 둔 원격 main 정보다. 최신 정보를 받은 뒤 내 작업 브랜치에도 반영한다.

1. **내 변경부터 확인한다.** `git status --short --branch`로 현재 브랜치와 저장하지 않은 변경을 살핀다. 진행 중인 변경이 있으면 내용을 확인하고 자기 작업을 커밋 등으로 보존한 뒤 코드를 합친다. 다른 사람의 작업 폴더를 바꾸거나 강제 초기화하지 않는다.
2. **원격의 최신 코드를 받는다.** `git fetch origin`을 실행한다. 이 명령은 원격 정보를 받아 두는 단계이며, 현재 작업 파일에 최신 main을 반영하는 단계도 아래에서 진행해야 한다.
3. **함께 진행 중인 PR을 확인한다.** GitHub의 Pull requests 목록을 보고, 다른 사람이 올린 최신 PR은 본문 → Files changed(바뀐 파일과 실제 diff) → Checks(자동 검사 결과)를 직접 읽는 것을 권한다. 내 작업과 관련되거나 파일이 겹치는 PR은 반드시 읽고 담당 범위·의존 관계·병합 순서를 Issue에 적는다. 아직 검토 중인 코드는 합의한 순서에 따라 반영하며, 관련 없는 작업은 계속할 수 있다.
4. **작업 파일에도 최신 main을 반영한다.** 새 작업은 최신 `origin/main`에서 브랜치를 만든다. 같은 작업을 이어갈 때는 자기 변경을 보존한 상태에서 `git merge origin/main`으로 최신 main을 합친다. 충돌이 나면 양쪽 변경의 의도를 확인해 해결하고, 해결하기 전에는 그 부분의 수정을 진행하지 않는다.

먼저 아래 두 명령으로 상태와 최신 코드를 확인한다.

```powershell
git status --short --branch
git fetch origin
```

새 작업이라면 아래처럼 브랜치를 만든다. `123`과 `short-name`은 실제 Issue 번호와 작업 이름으로 바꾼다.

```powershell
git switch -c task/123-short-name origin/main
```

같은 작업을 이어가는 경우에는 현재 작업 브랜치에서 실행한다.

```powershell
git merge origin/main
```

GitHub CLI가 있으면 `gh pr list --state open --limit 10`으로 열린 PR을 볼 수 있다. CLI가 없어도 GitHub의 Pull requests 화면에서 최근에 올라오거나 바뀐 PR을 확인할 수 있다. PR 제목이나 AI의 요약만으로 확인을 끝내지 않는다.

자기 AI에 아래 요청과 **이번 Issue 링크**를 함께 전달하면 된다. 이전 채팅 전문이나 개인 설정 파일은 전달하지 않는다.

```text
이 저장소의 AGENTS.md와 docs/development/team-workflow.md를 먼저 읽어줘.
이번 Issue의 목적·수정 범위·완료 기준과 관련 PR을 확인하고,
내 변경을 먼저 확인한 뒤 원격 최신 코드를 받아 작업 기준에 반영해줘.
열린 PR 목록과 다른 사람의 최신 PR을 직접 확인하고, 겹치는 작업과 진행 순서를 알려줘.
어디까지 검증됐는지와 남은 조건을 구분하고, 내 범위만 수정해줘.
기존 연동과 데이터를 유지하고, 바꾼 의도·사용 흐름·선택의 장단점·확인 결과를 쉬운 말로 PR에 남겨줘.
실제 AI 시험·계정 승인·새 배포는 이번 Issue의 권한과 예산을 먼저 확인해줘.
```

## 제작 컨벤션

새로 작성하거나 필요한 부분을 수정할 때 적용한다. 기존 파일 전체를 규칙에 맞춰 다시 쓰지 않는다.

| 항목 | 공동 기준 |
| --- | --- |
| 작업 시작 | 매번 [작업 시작 절차](#매번-작업을-시작하거나-이어갈-때)에 따라 최신 원격 코드를 받고 작업 파일에 반영한다. 열린 PR과 관련 작업을 먼저 확인한다. |
| 설명과 요약 | 개발을 처음 배우는 팀원을 기준으로 목적과 사용자 행동부터 설명한다. 중요한 용어는 처음 나올 때 풀어 쓰고, 선택한 이유와 의미 있는 장단점을 함께 적는다. |
| 코드 표기 | TS·JS는 2칸, Rust는 4칸 들여쓰기. 복잡한 조건·비동기 처리는 여러 줄로 나눠 판단과 실패 처리가 보이게 쓴다. |
| 수정 범위 | 기능 변경과 대규모 정리·파일 이름 변경을 섞지 않는다. 파일 전체 자동 포맷을 하지 않고 수정한 부분은 주변 문맥과 맞춘다. |
| 파일·이름 | 컴포넌트는 PascalCase, 훅은 `use…`로 작성한다. 기존 파일은 이유 없이 이름을 바꾸지 않는다. |
| 화면 | 기존 색상·간격·버튼을 재사용하고 담당 CSS의 기존 선언을 수정한다. 같은 요소를 덮는 보정 CSS나 전역 선택자를 계속 추가하지 않는다. |
| 연결·상태 | 변경 전 대상·개정을 확인하고 중복 클릭을 막는다. 대상 전환 뒤 늦은 응답은 폐기하고 실제 확인을 받은 뒤 성공을 표시한다. |
| 원본 보존 | 스킬 원본·라이선스·버전 보관본·생성물을 임의 포맷하거나 해시를 새로 맞추지 않는다. [Git 바이트 보존 규칙](../../.gitattributes)을 유지한다. |
| 의존성 | 기존 기능으로 해결하기 어려운 이유가 있을 때만 새 라이브러리를 추가한다. 의존성·잠금 파일 변경은 공통 파일 조정에 포함한다. |

이번에는 새 formatter·lint 도구, 타입 구조 개편, 전역 리팩터링을 도입하지 않는다. 일반 소스의 가독성 규칙을 원본·생성물의 바이트 보존보다 우선하지 않는다.

| --- | --- |
| [README](../../README.md) | 지금 사용 가능한 제품·시작 방법·지원 제한. 세부 작업 일지는 넣지 않는다. |
| 이 안내와 [AGENTS](../../AGENTS.md) | 오래 유지할 목표·규칙·검증 경계. 합의가 바뀔 때만 갱신한다. |
| GitHub Issue | 작업 목적·사람 담당자·범위와 제외·완료 기준·선행 작업·진행 상태·중요 결정. |
| GitHub PR | 실제 변화·Before/After·검사·제한·검토 요청·다음 AI 인계. |
| `docs/testing/` | 재현 환경·소스·명령·결과·증거 수준을 남기는 검수 기록. |
| `work/` | 비공개 원본·로컬 진단·작업 중 자료. 공유 자료를 여기로만 링크하지 않는다. |

같은 진행 상태를 여러 문서에 복제하지 않는다. Issue는 “할 일”, PR은 “실제로 바뀐 것”, 검사 기록은 “확인한 사실”의 기준이다. 중요한 제품·계약 결정은 Issue에 **결론·이유·영향 범위·합의한 사람·날짜**만 짧게 남긴다. 카카오톡·회의 원문이나 개인 AI 대화를 통째로 옮기지 않는다.

## 작업 한 번의 순서

### 큰 변경은 먼저 회의

**큰 변경은 수정 줄 수가 아니라 사용자·데이터·다른 작업에 미치는 영향으로 판단한다.** 아래 변경은 구현 전에 사람이 회의에서 합의한다. 카카오톡은 안건과 회의 결론을 공유하는 데 사용하고, AI가 회의나 합의를 대신하지 않는다.

| 사전 회의가 필요한 변경 | 예시 |
| --- | --- |
| 제품 방향·주요 사용자 흐름 | 대상 사용자·핵심 가치 변경, 전체 화면 구조 개편, 요청 전달·승인 순서 변경 |
| 공유 계약·데이터 | 공개 API·DB 형식 변경, 저장 위치·앱 식별자 변경, 기존 데이터 이관·삭제 |
| 실행·연결·권한의 원칙 | 호스트 연결 방식, 라우팅 원칙·지원 범위, 인증·보안·권한 처리 변경 |
| 비용·외부 서비스 의존 | 새 유료 서비스 도입, 외부 계정 필수화, 대화·사용자 데이터의 외부 전송 추가 |

기존 흐름·계약·데이터를 유지하는 문구·국소 배치·스타일 개선과 명백한 오류 수정은 담당 범위에서 먼저 만들고 전후 비교로 공유한다. 같은 변경을 여러 작은 PR로 나눠 사전 논의를 생략하지 않는다. 판단이 애매하면 영향과 선택지를 먼저 알린다.

**합의가 필요한 부분만 보류한다.**

1. 담당자는 기존 Issue에 **결정할 질문·권장안과 대안·영향·보류 범위·계속할 독립 작업**을 짧게 남기고 논의를 요청한다.
2. 해당 변경과 그 결정에 의존하는 구현만 기다린다. 현재 계약 안에서 완료할 수 있는 문구 정리·독립 오류 수정·기존 동작 검사·비파괴적 조사 등은 계속한다. 다른 담당 파일은 합의 없이 수정하지 않는다.
3. 미합의 방식을 제품 코드·저장 데이터·기본 동작에 먼저 적용하지 않는다. 그 결정을 전제로 만드는 구현은 독립 작업으로 취급하지 않는다.
4. 회의 후 **결론·이유·영향 범위·합의한 사람·날짜**를 Issue에 남기고, 바뀐 범위·선행 작업을 확인해 해당 부분을 재개한다. 침묵·시간 경과·AI의 추천은 합의가 아니다. 결론이 바뀌거나 범위가 늘면 추가되는 부분을 다시 논의한다.

회의 기록은 기존 Issue에 남기며 별도 승인 문서나 필수 PR 항목을 늘리지 않는다. 비용 집행·계정 승인 등 별도 권한이 필요한 행동은 회의 합의와 해당 행동의 승인을 구분한다.

### 작업 진행

1. **담당과 범위:** [작업 양식](../../.github/ISSUE_TEMPLATE/implementation.yml)으로 Issue를 만든다. 사람 담당자·수정 범위·완료 기준을 정하고 자기 AI에 Issue 링크를 준다. 동적 담당이므로 고정 직책이나 CODEOWNERS는 두지 않는다.
2. **시작·재개:** [작업 시작 절차](#매번-작업을-시작하거나-이어갈-때)에 따라 내 변경 확인 → 원격 최신 코드 받기 → 열린 PR 확인 → 작업 기준에 최신 main 반영을 마친다. 관련 PR은 본문·실제 diff·검사까지 읽고 링크와 진행 순서를 적는다. 각자 별도 클론 또는 worktree의 `task/<Issue번호>-<짧은이름>` 브랜치를 사용하고 다른 사람의 작업 중 체크아웃을 함께 수정하지 않는다.
3. **작게 먼저:** 위 기준 안의 작은 개선은 먼저 만들고 공유한다. 큰 변경은 사전 회의 후 결론을 Issue에 남긴다. 합의가 필요한 변경과 그 의존 구현만 보류하고 독립 작업은 계속한다. 공통 스타일·의존성·`package.json`·`pnpm-lock.yaml`·workspace·CI 설정처럼 겹치는 파일은 작업마다 조정 담당자와 수정 순서를 정한다. 고정 담당자를 새로 두지 않는다.
4. **변경과 근거:** 담당 범위만 고치고 필요한 검사와 같은 조건의 Before/After를 남긴다. 자기 AI의 하위 에이전트끼리는 파일 소유권을 나누며 공통 파일은 통합 담당자만 수정한다.
5. **PR과 인계:** 아래 형식을 사용하고 미완성은 Draft로 공유한다. 중단·담당 교체 때 접힌 “개발 기록과 다음 작업”에 **원격 브랜치·마지막 공유 상태·남은 로컬 변경·바로 다음 행동**을 갱신한다. 필요한 버전은 PR 커밋이나 검사 링크로 연결한다. 이전 AI의 수정을 멈춘 뒤 새 담당자가 이어받는다. 공유하지 못한 로컬 내용을 공유 완료로 표시하지 않는다.
6. **사람 검토와 병합:** 다른 사람 한 명이 화면·변경·검사·제한을 보고 승인한다. 승인 뒤 동작·계약이 바뀌면 변경점을 알리고 관련 부분을 다시 검토받는다. 오래된 승인·검사·캡처를 새 변경의 근거로 재사용하지 않는다. 담당자가 충돌과 최종 커밋 기준을 확인하고 병합한다. AI 검토는 사람 승인을 대신하지 않는다.

마무리할 때 **구현 완료 / 병합 완료 / 배포 완료**를 구분한다. 배포 완료에는 어느 설치본이 공개됐는지 남긴다. 문제가 생기면 영향 범위와 해당 변경을 되돌리는 방법을 PR에 남기고 복구한다. 공유 기록의 강제 초기화나 사용자 데이터 삭제를 기본 해결법으로 삼지 않는다. 작은 작업 원칙은 [DORA의 작은 변경 단위 안내](https://dora.dev/capabilities/working-in-small-batches/)를 참고한다.

2026-10-28 기준 쓰기 권한은 소유자 한 명이고 `main` 보호는 아직 설정되지 않았다. 위 승인은 공동 작업 규칙이며 GitHub가 현재 강제하는 설정은 아니다. 다른 두 사람의 쓰기 권한이 준비되면 타인 한 명의 승인과 필수 검사 통과를 요구하도록 브랜치 보호를 설정한다. 이 문서 작업에서 초대나 권한 변경을 대신 수행하지 않는다.

2026-11-03에 소유자가 PR #22의 보완과 병합을 직접 요청했다. 해당 PR은 이 요청을 기록하고 최종 검사 통과 뒤 병합한다. 동료의 리뷰 승인이 있었다는 뜻은 아니며, 이후 작업의 타인 한 명 검토 규칙은 유지한다. 같은 날 `main` 보호가 설정되지 않은 것을 재확인했으며 권한 설정은 변경하지 않는다.

## PR 설명 작성하기

[공통 PR 양식](../../.github/pull_request_template.md)의 순서를 유지한다.

1. **한눈에 보기:** 누가 어떤 불편을 겪었고 이번에 무엇이 달라지는지 두세 문장으로 요약한다. 관련 Issue와 담당자를 연결한다.
2. **사용 흐름과 전후 비교:** 같은 상황에서 사용자가 무엇을 누르고 어떤 결과를 받는지 이전과 변경 후의 순서로 설명한다. 화면은 같은 조건의 이미지, 움직임과 흐름은 짧은 영상도 함께 보여준다. 화면이 없는 기능과 문서는 전후 설명 표로 비교한다.
3. **바꾼 내용과 이유:** 중요한 변화 1~3개를 행동과 목적 중심으로 풀어 쓴다. 왜 이 방법을 골랐는지, 좋아지는 점과 대신 감수하는 점도 적는다. 의미 있는 장단점이 없는 작은 수정에 억지로 대안을 만들 필요는 없다.
4. **확인한 내용과 남은 점:** 확인한 내용과 결과, 실패하거나 아직 확인하지 않은 부분을 구분한다. 자동 검사·실제 앱 사용·설치·배포를 각각 설명하고, 상세 명령과 로그는 개발 기록이나 검사 문서로 연결한다.
5. **함께 확인할 점:** 검토자가 봐 주었으면 하는 지점이나 결정할 내용을 1~3개 적는다.

개발 용어를 아는 사람만 이해하는 파일·함수 목록으로 본문을 채우지 않는다. 예를 들어 “설정을 별도 창으로 옮겨 기본 화면을 간단하게 했어요. 대신 설정을 바꾸려면 버튼을 한 번 더 눌러야 해요.”처럼 의도와 사용 흐름, 선택의 장단점을 연결한다. 작은 변경은 짧게 쓰고 같은 설명을 여러 목차에서 반복하지 않는다.

**본문에 기준 소스·변경 소스의 커밋 번호를 따로 나열할 의무는 없다.** 비교한 버전은 PR의 커밋 목록·검사 링크로 확인하고, 별도 버전을 쓴 자료는 검사 문서나 접힌 **개발 기록과 다음 작업**에 연결한다. 비교 조건·근거 수준·영향 범위·유지할 계약·확인한 것·남은 것·이어서 할 일은 그 접힌 영역에 모은다. 인계에 필요한 브랜치와 미공유 변경도 여기에 남긴다.

`pnpm review:check --body <본문파일>`로 양식과 비교/개발 기록의 누락을 점검한다. 작성 중인 PR은 기존 제목과 “다음 AI에게” 형식으로도 검사할 수 있으므로 이번 규칙을 적용하려고 다른 사람의 PR을 억지로 고치지 않는다. 설명이 친절한지와 장단점을 제대로 짚었는지, 근거가 사실인지는 사람이 확인한다. 검사기와 검사 워크플로 변경도 PR 검토를 거치며, 자동 검사는 검토를 돕는 보조 수단으로 사용한다. 작은 변경에 별도 보고서나 긴 결정 문서를 만들 필요는 없다.

## Before/After와 Agentation 공유

공유할 이미지는 필요한 것만 `docs/changes/<작업번호>/`에 둔다. 새 작업은 Issue 번호를 쓰며, 기존 PR #22의 자료 정리는 `docs/changes/22/`를 그대로 사용할 수 있다. 이를 위해 새 Issue를 만들 필요는 없다. `before.png`, `after.png`처럼 구분하고 PR에는 저장소 상대 경로나 GitHub 첨부를 사용한다. 짧은 영상은 GitHub 첨부로 공유하고 저장소에 넣지 않는다. 화면 크기·배율·데이터·상태를 맞추고 **실제 실행 / 합성 검사 / 디자인 예시**를 구분한다. 비교한 버전과 상세 조건은 검사 문서나 접힌 개발 기록에 남기며 PR 본문에 커밋 번호를 반복하지 않아도 된다. 문서 변경은 전후 설명과 **문서 검토**로 비교한다. 개인정보·대화 본문·인증값·개인 경로를 제거한다. 이전 화면을 확보하지 못했으면 사실을 쓰거나 정확한 기준 버전에서 재현하고, 전후 효과를 꾸미지 않는다.

Agentation의 localhost 의견과 `~/.agentation/store.db`는 **각 PC의 로컬 자료**다. 다른 사람·AI에게 자동 공유되지 않는다. 공유할 의견은 Issue/PR에 **요약·페이지·고정 요소 ID·원하는 변화·비식별 캡처**를 옮긴다. 주석 ID는 로컬 추적용으로만 함께 적는다. 원본 의견·로컬 설정은 공개하지 않는다. UI 영역별 작업은 [화면 공동 규칙](ui-collaboration.md)과 [파일 목록](ui-ownership.json)을 따른다.

## 새 AI에게 넘길 때

**이 안내 → Issue → 관련 PR·diff → 검사 결과**를 읽게 한다. [작업 시작 절차](#매번-작업을-시작하거나-이어갈-때)에 따라 현재 브랜치와 작업 중 변경을 보존하고 최신 코드를 반영하게 한다. PR의 “개발 기록과 다음 작업”에서 미완료와 다음 행동을 갱신한다. 새 AI가 이전 대화를 읽어야만 이해되는 결정을 남기지 않는다.

[옛 병렬 개발표](../roadmap/parallel-development.md)와 [2026-09-22 상태 스냅샷](../implementation-status.json)은 역사 기록이다. 현재 담당·지원 상태·설치 승인 범위를 정하는 자료로 쓰지 않는다.
