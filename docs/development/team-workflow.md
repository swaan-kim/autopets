# 세 사람과 각자의 AI가 함께 만드는 AutoPets

**한 작업 · 사람 담당자 한 명 · 브랜치 하나 · PR 하나.** 변경 이유와 결과는 사람이 한눈에 보고, 다음 AI는 이전 대화를 몰라도 이어갈 수 있게 남긴다.

## 함께 지킬 제품 방향

AutoPets는 **좋은 스킬과 작업 설정을 쉽게 쓰고, 하던 일을 펫과 이어가는 서비스**다. 첫 대상은 Windows Codex를 이미 사용하지만 스킬·프롬프트·모델 설정에는 익숙하지 않은 사람이다. 마케팅·운영 담당자는 우선 타겟 가설이며 확정된 수요로 취급하지 않는다. 행사·캠페인 페이지는 대표 과제이며 제품 전체를 웹페이지 제작 도구로 제한하지 않는다.

기본 흐름은 **Codex에서 펫 호출 → 앱·오버레이 → 펫 선택·현재 채팅에 적용 → 같은 채팅에서 요청 → 진행 확인 → 결과·하던 작업 복귀**다. 할 일은 Codex에서 입력하고, 앱은 선택·설정·상태·재사용에 집중한다. 정상 연결 뒤 수동 복붙이나 화면 자동 조작을 요구하지 않는 경로를 우선한다.

- 설명보다 펫·결과·다음 행동을 먼저 보여준다. 화이트·뉴트럴 화면과 기존 입체 강아지를 유지한다.
- 처음 성공하는 편의, 정확한 작업 재개, 같은 설정 재사용을 우선한다. 새 펫·서비스·꾸미기 확대는 별도 결정이다.
- 개선 순서는 **작업을 막는 문제 → 잘못된 상태 → 불필요한 조작 → 시각적 완성도**다. 사용자 변화 하나를 작업 단위로 잡고 관련 없는 기능 확장을 섞지 않는다.
- 현재 방식은 **펫 하위 작업의 모델·강도 라우팅과 계획 프롬프트**다. 자동 훅·부모 모델 변경·실제 Plan 강제를 약속하지 않는다.
- 대상 ID·폴더·개정 확인, 데이터 보존, 채팅 격리, 중복 실행 방지는 시각 개선보다 우선한다. 보안·신뢰 승인을 우회하지 않는다.

## 제작 컨벤션

새로 작성하거나 필요한 부분을 수정할 때 적용한다. 기존 파일 전체를 규칙에 맞춰 다시 쓰지 않는다.

| 항목 | 공동 기준 |
| --- | --- |
| 코드 표기 | TS·JS는 2칸, Rust는 4칸 들여쓰기. 복잡한 조건·비동기 처리는 여러 줄로 나눠 판단과 실패 처리가 보이게 쓴다. |
| 수정 범위 | 기능 변경과 대규모 정리·파일 이름 변경을 섞지 않는다. 파일 전체 자동 포맷을 하지 않고 수정한 부분은 주변 문맥과 맞춘다. |
| 파일·이름 | 컴포넌트는 PascalCase, 훅은 `use…`로 작성한다. 기존 파일은 이유 없이 이름을 바꾸지 않는다. |
| 화면 | 기존 색상·간격·버튼을 재사용하고 담당 CSS의 기존 선언을 수정한다. 같은 요소를 덮는 보정 CSS나 전역 선택자를 계속 추가하지 않는다. |
| 연결·상태 | 변경 전 대상·개정을 확인하고 중복 클릭을 막는다. 대상 전환 뒤 늦은 응답은 폐기하고 실제 확인을 받은 뒤 성공을 표시한다. |
| 원본 보존 | 스킬 원본·라이선스·버전 보관본·생성물을 임의 포맷하거나 해시를 새로 맞추지 않는다. [Git 바이트 보존 규칙](../../.gitattributes)을 유지한다. |
| 의존성 | 기존 기능으로 해결하기 어려운 이유가 있을 때만 새 라이브러리를 추가한다. 의존성·잠금 파일 변경은 공통 파일 조정에 포함한다. |

이번에는 새 formatter·lint 도구, 타입 구조 개편, 전역 리팩터링을 도입하지 않는다. 일반 소스의 가독성 규칙을 원본·생성물의 바이트 보존보다 우선하지 않는다.

| 위치 | 남길 내용 |

| GitHub Issue | 작업 목적·사람 담당자·범위와 제외·완료 기준·선행 작업·진행 상태·중요 결정. |
| GitHub PR | 실제 변화·Before/After·검사·제한·검토 요청·다음 AI 인계. |
| `docs/testing/` | 재현 환경·소스·명령·결과·증거 수준을 남기는 검수 기록. |
| `work/` | 비공개 원본·로컬 진단·작업 중 자료. 공유 자료를 여기로만 링크하지 않는다. |

같은 진행 상태를 여러 문서에 복제하지 않는다. Issue는 “할 일”, PR은 “실제로 바뀐 것”, 검사 기록은 “확인한 사실”의 기준이다. 중요한 제품·계약 결정은 Issue에 **결론·이유·영향 범위·합의한 사람·날짜**만 짧게 남긴다. 카카오톡·회의 원문이나 개인 AI 대화를 통째로 옮기지 않는다.

## 작업 한 번의 순서

1. **담당과 범위:** [작업 양식](../../.github/ISSUE_TEMPLATE/implementation.yml)으로 Issue를 만든다. 사람 담당자·수정 범위·완료 기준을 정하고 자기 AI에 Issue 링크를 준다. 동적 담당이므로 고정 직책이나 CODEOWNERS는 두지 않는다.
2. **시작·재개:** 최신 원격 상태·기준 커밋·겹치는 작업을 확인하고 미커밋 변경을 보존한다. 선행 PR이 있으면 링크와 병합 순서를 적는다. 각자 별도 클론 또는 worktree의 `task/<Issue번호>-<짧은이름>` 브랜치를 사용하고 다른 사람의 작업 중 체크아웃을 함께 수정하지 않는다.
3. **작게 먼저:** 일반적인 문구·배치·구현은 작은 시제품을 먼저 공유한다. API·DB·연결 계약·제품 방향은 먼저 합의하고 Issue에 남긴다. 공통 스타일·의존성·`package.json`·`pnpm-lock.yaml`·workspace·CI 설정처럼 겹치는 파일은 작업마다 조정 담당자와 수정 순서를 정한다. 고정 담당자를 새로 두지 않는다.
4. **변경과 근거:** 담당 범위만 고치고 필요한 검사와 같은 조건의 Before/After를 남긴다. 자기 AI의 하위 에이전트끼리는 파일 소유권을 나누며 공통 파일은 통합 담당자만 수정한다.
5. **PR과 인계:** 아래 형식을 사용하고 미완성은 Draft로 공유한다. 중단·담당 교체 때 기존 “다음 AI에게”에 **원격 브랜치·마지막 공유 커밋·남은 로컬 변경·바로 다음 행동**을 갱신한다. 이전 AI의 수정을 멈춘 뒤 새 담당자가 이어받는다. 공유하지 못한 로컬 내용을 공유 완료로 표시하지 않는다.
6. **사람 검토와 병합:** 다른 사람 한 명이 화면·변경·검사·제한을 보고 승인한다. 승인 뒤 동작·계약이 바뀌면 변경점을 알리고 관련 부분을 다시 검토받는다. 오래된 승인·검사·캡처를 새 변경의 근거로 재사용하지 않는다. 담당자가 충돌과 최종 커밋 기준을 확인하고 병합한다. AI 검토는 사람 승인을 대신하지 않는다.

마무리할 때 **구현 완료 / 병합 완료 / 배포 완료**를 구분한다. 배포 완료에는 어느 설치본이 공개됐는지 남긴다. 문제가 생기면 영향 범위와 해당 변경을 되돌리는 방법을 PR에 남기고 복구한다. 공유 기록의 강제 초기화나 사용자 데이터 삭제를 기본 해결법으로 삼지 않는다. 작은 작업 원칙은 [DORA의 작은 변경 단위 안내](https://dora.dev/capabilities/working-in-small-batches/)를 참고한다.

2026-10-28 기준 쓰기 권한은 소유자 한 명이고 `main` 보호는 아직 설정되지 않았다. 위 승인은 공동 작업 규칙이며 GitHub가 현재 강제하는 설정은 아니다. 다른 두 사람의 쓰기 권한이 준비되면 타인 한 명의 승인과 필수 검사 통과를 요구하도록 브랜치 보호를 설정한다. 이 문서 작업에서 초대나 권한 변경을 대신 수행하지 않는다.

## PR은 이 정도만

[공통 PR 양식](../../.github/pull_request_template.md)의 순서를 유지한다.

- **무엇이 좋아졌나:** 사용자에게 달라진 점 한두 줄.
- **Before → After:** UI는 전후 이미지, 기능은 같은 입력의 전후 동작·출력. 해당하지 않으면 이유를 적는다.
- **핵심 변경:** 동작·파일·계약에 영향을 주는 점만.
- **검사와 제한:** 수행 결과와 미수행 이유. 합성 검사와 실제 설치·채팅 검사를 구분한다.
- **검토 요청:** 다른 사람이 결정하거나 확인할 점.
- **다음 AI에게:** 접힌 영역에 기준·최종 커밋, 범위, 결정, 유지할 계약, 완료·미완료, 다음 행동과 관련 링크.

`pnpm review:check --body <본문파일>`로 양식과 근거 표기의 누락을 점검한다. 실제 동작·개인정보 안전·사람 승인은 별도 검토한다. 검사기와 검사 워크플로 변경도 PR 검토를 거치며, 자동 검사는 검토를 돕는 보조 수단으로 사용한다. 작은 변경에 별도 보고서나 긴 결정 문서를 만들 필요는 없다.

## Before/After와 Agentation 공유

공유할 이미지는 필요한 것만 `docs/changes/<작업번호>/`에 둔다. 새 작업은 Issue 번호를 쓰며, 기존 PR #22의 자료 정리는 `docs/changes/22/`를 그대로 사용할 수 있다. 이를 위해 새 Issue를 만들 필요는 없다. `before.png`, `after.png`처럼 구분하고 PR에는 저장소 상대 경로나 GitHub 첨부를 사용한다. 짧은 영상은 GitHub 첨부로 공유하고 저장소에 넣지 않는다. 화면 크기·배율·데이터·상태를 맞추고 기준/최종 커밋과 **실제 실행 / 합성 검사 / 디자인 예시**를 적는다. 개인정보·대화 본문·인증값·개인 경로를 제거한다. 이전 화면을 확보하지 못했으면 사실을 쓰거나 정확한 기준 커밋에서 재현하고, 전후 효과를 꾸미지 않는다.

Agentation의 localhost 의견과 `~/.agentation/store.db`는 **각 PC의 로컬 자료**다. 다른 사람·AI에게 자동 공유되지 않는다. 공유할 의견은 Issue/PR에 **요약·페이지·고정 요소 ID·원하는 변화·비식별 캡처**를 옮긴다. 주석 ID는 로컬 추적용으로만 함께 적는다. 원본 의견·로컬 설정은 공개하지 않는다. UI 영역별 작업은 [화면 공동 규칙](ui-collaboration.md)과 [파일 목록](ui-ownership.json)을 따른다.

## 새 AI에게 넘길 때

**이 안내 → Issue → 관련 PR·diff → 검사 결과**를 읽게 한다. 그다음 현재 브랜치·기준 커밋·작업 중 변경을 확인하고 범위 밖 파일을 보존하게 한다. PR의 “다음 AI에게”에서 미완료와 다음 행동을 갱신한다. 새 AI가 이전 대화를 읽어야만 이해되는 결정을 남기지 않는다.

[옛 병렬 개발표](../roadmap/parallel-development.md)와 [2026-09-22 상태 스냅샷](../implementation-status.json)은 역사 기록이다. 현재 담당·지원 상태·설치 승인 범위를 정하는 자료로 쓰지 않는다.
