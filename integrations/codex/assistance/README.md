# Codex 자동 도움 연결 코드

이 연결은 새 설정·SQLite API와 공통 작업 규칙을 사용한다. 기존 `probe/`는 과거 M1 재현용이며 동시에 준비 훅을 설치하지 않는다. 관측 훅과 준비 훅은 계속 분리한다.

현재 배포 capabilities는 미검증이다. 일반 모드에서는 추가 지침을 출력하지 않는다. 실제 검증 담당자가 프로젝트에 `--validation`으로 명시적으로 연결했을 때만 진단용 지침이 나온다. 본 변경에서 사용자 환경에 설치하거나 trust를 바꾸지 않았다.

## 검증 준비

1. 새 빌드의 앱을 테스트 환경에서 실행하고 추천 설정을 켠다.
2. `node integrations/codex/assistance/setup.mjs --project <절대 경로> --connection <connection.json 절대 경로> --validation`으로 변경 계획을 확인한다. 기본은 dry-run이다.
3. 별도 승인된 설치 단계에서 같은 명령에 `--apply`를 넣는다. CLI `/hooks`에서 정확한 정의를 검토한다. 기존 M1 준비 훅은 해당 제거 도구로 제거하고 관측 훅은 유지한다.
4. 스킬 호출 없이 두 실제 Codex 채팅으로 요청, 조건 변경, 재개, 압축 복구를 검증한다. 훅 stdout·전송 receipt와 실제 모델의 지침 수신 증거는 구분한다.
5. 제거는 `--project <경로> --remove --apply`. 타인의 훅·기록·신뢰 설정은 삭제하지 않는다.

## 기록과 부담

- 세션 ID의 해시를 계정 미확인 범위로 사용해 채팅끼리 내용을 공유하지 않는다. 이는 로그인 계정 확인 증거가 아니다.
- 요청 원문은 메모리에서 규칙 분류에만 사용한다. 훅 이벤트와 API에는 원문·도구 출력·대화 기록을 전달하지 않는다.
- 준비 지침은 UTF-8 3KB 이하. 설정·기록·절차·복구 상태가 같으면 추가 지침을 생략한다.
- 응답 길이는 기본 `concise`, 결과 형식은 기본 `adaptive`다. 최신 사용자 요청을 우선하고, 작업의 `workStyleOverride`가 있으면 전역 작업 방식보다 우선한다. 답변 길이·형식은 작업에서 임의로 덮어쓰지 않는다.
- `settingsRevision`을 준비 요청에 함께 보내 설정 변경과 경쟁한 오래된 지침을 거절한다. 적용할 설정과 문맥 개정 번호가 바뀌면 중복 판정을 다시 한다.
- 3KB 안에 저장 문맥을 전부 넣을 수 없으면 `contextPartial`과 `includedContextKeys`를 보내고 지침에도 일부 생략을 명시한다. 키 목록은 해당 필드 전체가 포함된 경우만 가리킨다. 필요한 누락 조건은 기존 실행에서 `inspect`로 읽고, 확인할 수 없으면 추정하지 않는다.
- 기존 실행 모델이 조건이나 결정의 의미 있는 변경을 기록할 때만 `inspect`/`record`를 사용한다. 기록 파일은 `.local/autopets-assistance/records/` 안의 짧은 구조화 JSON이며 Git에서 제외된다.
- JSON 파일은 임시 입력이다. 경로를 검증해 소비한 파일은 성공·실패에 관계없이 제거하며 재시도 시 새로 작성한다. 소비 전 연결 검사 실패나 프로세스 강제 종료로 남은 파일은 이 정리의 보장 범위가 아니다. 영구 업무 기록은 앱의 SQLite에서 관리한다.
- `record`는 CODEX_THREAD_ID, 프로젝트, 현재 관측 턴과 개정 번호를 검증한다. 새 모델 호출이나 반복 요약을 만들지 않는다.
- 현재 턴 종료만으로 목표 달성·모델 변경·전달 확인을 주장하지 않는다. 추가 지침은 현재 사용자 요청과 모드·권한을 우선한다.

정식 자동 지원 표시는 실제 두 채팅 검증 이후 코드의 capability 정책을 검토해 바꾼다. 임의 클라이언트 요청으로 capability를 활성화할 수 없다.

## 계획·실행과 제출 전 보호

- `/v1/workflow`의 작업별 opt-in과 개정된 계획 확인을 읽어 계획/실행 지침을 정한다. 짧은 번역·맞춤법·한 문장의 단순 수정만 계획을 건너뛰고, 요약·조사·문서 작성은 새 업무로 계획부터 준비한다. recipe 분류 자체는 계획 확인이 아니다.
- 현재 모델은 공식 훅 `model` 필드만 사용한다. 문서화되지 않은 `reasoning`, `reasoning_effort`, `collaboration_mode`와 `permission_mode`는 추론 수준이나 실제 Plan 협업 모드의 증거로 사용하지 않는다. 첫 줄 전체가 `모델: gpt-6-astra`, `/model gpt-6-astra`, `이번 요청은 Astra 모델로 진행해줘` 같은 명확한 모델 지시이면 canonical 4개 모델에 한해 요청 우선 선택으로 보낸다. 인용·본문 언급을 모델 지시로 추출하지 않는다.
- 준비 훅과 비동기 관측 훅은 동일한 `session_id`·`turn_id`·요청문 해시로 같은 제출 ID를 만든다. 원문은 저장·전송하지 않는다. 제출 보류 판정은 `turn_started` 및 준비/전달 receipt보다 먼저 처리된다. 관측 훅 출력은 언제나 `{}`이고, 동기 준비 훅만 공식 `{decision:"block",reason}`를 출력한다.
- `workflowBinding`은 제출 ID·계획/설정 개정번호·단계·확인을 준비 nonce에 묶는다. 검사 직후 사용자가 계획이나 설정을 바꾸면 backend는 오래된 지침 준비와 전달 기록을 거절한다. 지침 해시만으로 최신성을 추정하지 않는다.
- 제출 보호는 동기 준비 훅이 실제 설치·신뢰되고 같은 제출을 처리한다는 증거, 모델 관측, 선택 모델/추론의 실제 가용성, 입력과 첨부 보존, 재개 시 한 번 전송 검증이 모두 필요하다. 비동기 관측 훅 하나로 보호가 된다고 표시하면 안 된다. 현재 서버 capability는 모두 미검증이며 가용 모델 목록은 비어 있다. 설정을 저장하거나 fixture가 통과해도 이 값은 승격되지 않는다.
- 공식 훅은 첨부파일 신원 또는 첨부 없는 요청인지 알려주지 않는다. 요청문 해시는 완전한 요청 identity가 아니다. 따라서 현재 훅은 `requestIdentity` 검증이나 한 번 예외 사용을 증명할 수 없다. 이는 별도 `verified-adapter`가 현재 요청 전체 또는 검증된 텍스트 전용 제출을 보증해야 한다. 첨부가 바뀐 요청에 이전 예외를 재사용하면 안 된다.
- 장애·모르는 입력·미검증 보호는 원래 전송을 막지 않는다. `보호 확인 불가`이며 관측 이벤트는 기존대로 유지한다. 모델·추론·모드 자동 변경, 프롬프트·첨부 재작성, 응답 중단은 이 연결에서 구현하지 않는다.

## 현재 실행에서 계획 기록

`prepare.mjs plan-inspect --config <설정 절대 경로>`는 현재 `CODEX_THREAD_ID`와 관측 턴을 대조하고 계획/설정 개정번호를 반환한다. 실제로 제시한 계획만 `{expectedSettingsRevision,expectedPlanRevision,plan:{summary,steps,completionCriteria}}` 구조로 `.local/autopets-assistance/records/` 안의 임시 JSON에 쓴 뒤 `plan-record --config <설정 절대 경로> --record <JSON 절대 경로>`로 기록한다. `summary`는 1024 UTF-8 바이트, 목록은 각각 최대 12개/항목 512바이트, 전체 plan은 3072바이트 이하이다. 이전 개정번호, 다른 채팅, 링크된 파일은 거절한다. 소비된 임시 입력은 성공·실패 모두 삭제한다.

계획 기록은 사용자 확인과 별개다. 구조화 계획을 읽지 못해도 사용자가 원래 채팅의 계획을 명시적으로 확인할 수 있으며, 그때 계획 요약을 만들어내지 않는다. 지침은 전체 3KB 한도 안에서 완전한 필드만 포함하고, 생략하면 본문 안내와 준비 `reason`의 `planPartial`/`includedPlanKeys`로 드러낸다. 필요한 조건은 같은 실행의 `plan-inspect`/`inspect`로 확인한다. 현재 모드에서 파일·도구 사용이 금지되면 기록을 생략하며 별도 모델 호출을 하지 않는다. 실행 후에는 같은 실행에서 완료 기준·형식·누락을 점검하고 추가 실행의 권한·지원이 없으면 미해결을 알린다.

공식 계약: [공통 훅 입력](https://learn.chatgpt.com/docs/hooks#common-input-fields), [UserPromptSubmit](https://learn.chatgpt.com/docs/hooks#userpromptsubmit). 실제 설치·동작 확인은 별도 승인된 검증 단계이다.
